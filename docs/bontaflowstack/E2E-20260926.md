# BontaFlowStack 0.1.4 Desktop test status

On 2026-09-26, a local Codex Desktop campaign assigned a result to every case in a **new 205-case inventory** covering the 40 installed skills. The earlier authoritative scenario file was unavailable, so these are reconstructed cases, not a rerun of its historical count. Each case used a small disposable fixture where possible. The detailed local evidence includes paths and test state and is not part of this repository.

| Result | Cases |
| --- | ---: |
| PASS for the specified narrow behavior | 125 |
| FAIL | 3 |
| PARTIAL | 4 |
| BLOCKED or NOT_RUN | 72 |
| OUT | 1 |

A PASS includes expected question, refusal, and error branches. It does not certify an entire skill. The chats ran in Codex Desktop, but captured records do not independently prove native skill-catalog activation; many tasks loaded instructions through the installed package's `read` command.

## Findings

- `C-careful-02`: A test chat observed that its native project marker differed from the nested fixture's safety status, then enabled `careful` anyway. This failed the skill's required stop condition. The low-level safety command does not compare the marker itself. The write was confined to isolated test state.
- `C-context-save-03`: The skill says to record unavailable Git state, but the packaged checkpoint helper rejected a non-Git project with `Git project required`. No checkpoint was written. Non-Git support needs an explicit product decision.
- `C-plan-tune-07`: An isolated config update failed in Git Bash with a permission error while creating a `/c/Users/...` path. The setting remained unchanged. The path conversion or child sandbox boundary is not yet resolved.
- Browser cleanup: A healthy test daemon started without a recorded process identity when the Windows CIM probe could not read its command line. The packaged `stop` command correctly refused an unverified process, but the daemon could not be cleaned up through that command. It remained running, occupying the default browser port. Later browser and render observations through that shared port were not accepted as isolated evidence.

Some test chats also wrote lifecycle events to the user's default local plugin state before per-case isolation was enforced. Those test records were preserved; subsequent unsafe child execution was stopped. This is a harness incident, not a plugin acceptance result.

**Verdict:** The owner's earlier v0.1.4 release decision remains a release decision. Full native Desktop E2E acceptance is **not established**. A follow-up build should address the findings, provide a safely stoppable isolated browser, and rerun blocked branches with observable native skill selection.
